Permanent tablet DX-spot display — worked-before & propagation

Date
2026-09-18
Topic
dx-spot-tablet-display
Focus
A permanent display of DX-cluster information much as Log4OM displays it — worked before, new band, new band mode — on a tablet, always at the same place; Wavelog mirror (or Log4OM remote API) as the worked-before source; rows carry call, flag, optional op name, age, comment, mode, band; plus propagation information.
Mode
Repo-grounded (stationa monorepo)
Run
40 raw ideas from 5 frames + 5 evidence dossiers + web research → 14 deduped candidates → adversarial basis verification (13 sound, 1 weak, 0 refuted) → 7 survivors · revised 2026-09-19: surface decided in review (browser board on :8091, dedicated second tablet)

Grounding Context

What the repo actually has today, and what the outside world already solved.

  • The bus has no DX-cluster source. muehle/hf/spots exists but carries one operator-selected station record (retained /state, role bandmap) from logger-spot-bridge — not a spot list. A draft, docs/logging-integration-model.md §6.3, defines an unbuilt non-retained …/spots/event stream (action/ts/dxcall/freq_hz/band/mode/spotter/comment/source/status) — and it contradicts its own idempotency rule ("Every event carries a stable id"): the drafted event has no id.
  • The console ACL makes the drafted stream invisible to the tablet. The seeded console account reads only muehle/+/+/state|meta|status (mqtt-broker/acl.conf.example); a 4-level …/spots/event matches no read rule, while a retained …/spots/state passes. (Seed-file verified; live broker — the HA add-on at 192.168.1.50 — not audited.)
  • hf_console already has the kiosk, but not permanence. Device-owner lock, KioskPolicy, immersive fullscreen, doze-proof MQTT recovery (fresh-client + pong watchdog), band-color palette, tablet reflow — all shipped. But keep-screen-on was deliberately removed (commit e05cf64): the display sleeps after 1 h of touch idle. A permanent board is never touched, so as shipped it goes dark every hour.
  • No spot table exists anywhere in hf_console. Spots render as 2.5 px canvas dots; the comment-bearing dxcluster source is discarded at ingest (dxspot_service.dart: if (sourceType != 'mqtt') return;). A mature aging/repaint vocabulary exists to reuse: fresh/stale/expired buckets, 30 s repaint keys, 500 ms notify throttle, stable-skeleton in-place updates (testui).
  • Worked-before has zero footprint (no ATNO/LoTW/DXCC-entity code anywhere). The station-proven pattern to copy is bridge-side QRZ enrichment (session key, disk cache 30 d / 10 min / 2000-cap, creds off device). Callsign request/reply was already explicitly deferred in the draft: "request/reply — awkward on MQTT".
  • Propagation is a documented zero — one unexplained hook ("horstprop Layer-3 modelling", deferred, never defined) and nothing else.
  • External: Wavelog API v2 /lookup?callsign=…&detail=full returns workedBefore + worked-on-band + worked-band-mode + confirmed flags + LoTW membership + DXCC payload with flag emoji in one call (no spots endpoint). Log4OM 2 has no consequential lookup API — its spot-panel lookups are display-only and never merged into outbound UDP; the canonical log-mirror path is Log4OM UDP out (WaveLogGate, port 2236) → Wavelog. Propagation's de-facto source is the hamqsl.com solar XML (~3 h cadence, incl. per-band day/night conditions); WWV/WCY messages already ride every cluster feed (QLog renders them as propagation views).
  • Prior art: wave-flex-integrator (per-spot Wavelog coloring), SpotCollector / N1MM+ bandmaps (color-against-log, update-in-place rows), dxwatch/hamspots (web walls), ESP32 spot boards, Ian Renton's telnet-cluster→MQTT "meta-spotter", QLog's WWV/WCY views. The departure-board/NOC-wall pattern (append-only rows, relative age, color-as-state, headline strip, dim schedule vs burn-in) is the working cross-domain template.

1

Bandmap-enricher logic slot

Axis: spot pipeline Confidence 85% Complexity M

Description. One new logic slot on shari — the antennaselect/powerseq species: no device, just a process — subscribes the spot stream, holds the worked-before state (idea 2), classifies each spot by in-memory set membership, and publishes a bounded top-N enriched bandmap as a single retained /state snapshot on a slow tick (5–10 s). Every display — the tablet, the :8091 web channel, testui, a future e-paper frame — becomes a dumb renderer of one retained payload. A tablet booting out of doze recovers into a full board from one retained message (hf_console's recovery model already ends in a fresh client), with no QoS-1 dedup, no replay windows, no reconnect machinery on any consumer. Worked verdicts ride asynchronously: the row appears the moment the spot lands, the ATNO badge pops in when classification catches up, and a slow or down logbook degrades to colorless rows — never to missing spots.

Basis

direct: the draft's "Consumers build their own bandmap from the event stream" is inverted by the draft's own retained-rollup rule ("the retained rollup a late joiner reads immediately … consumers couple to this, not to the fact an event was emitted"). The seeded console ACL reads muehle/+/+/state — a retained …/spots/state reaches the tablet today; the drafted event topic matches no read rule. The publish-anyway posture ("on lookup error the selection is published unchanged") is the station's existing degradation precedent. external: Kafka log-compaction / market-data snapshot-then-incremental; departure-board walls as dumb renderers of a maintained snapshot. Three ideation frames converged on this shape independently.

Rationale

This is the load-bearing architectural fork: events-first (the draft's current sentence) puts dedup/replay/recovery logic in every consumer forever and is invisible to the tablet under the seeded ACL; state-first makes the ACL problem vanish, makes every future DX surface free, and gives worked-before enrichment (idea 2) a natural home. It also forces a decision the docs currently encode as a collision — the bandmap role at …/spots is taken by logger-spot-bridge's selection record.

Downsides

Retained republish churn across the HA bridge every tick (small). No event history for future analytics — though "the logbook is the system of record, not the bus", and events can be added later without breaking state consumers. One more always-on process on shari.

2

Worked-before as a synced set, not a per-spot lookup

Axis: worked-before enrichment Confidence 85% Complexity M

Description. Don't ask the log about each spot — sync the log's worked matrix into the enrichment point and classify by set membership. Bulk-seed once from the Wavelog mirror (ADIF export or API): call → bands → modes, plus confirmed tiers and the DXCC-entity set (a lifetime log is a few MB of keys). Incremental deltas ride the drafted …/log/event stream as they land. Every spot then classifies in O(1): ATNO / new band / new mode / dupe / confirmed — and flips from ATNO to worked seconds after the QSO is logged (self-healing), instead of staying stale until a re-lookup. The user's named alternative — per-spot Wavelog /lookup — is demoted to op-name/callbook gap-fill on the jobs worker; the Log4OM remote API is consciously deprioritized (its lookups are display-only and never merged into outbound data).

Basis

direct: the repo already deferred callsign request/reply once ("request/reply — awkward on MQTT | deferred"); the QRZ disk-cache design (30 d positive / 10 min negative / 2000-cap, tmp+rename 0600, creds env-only) is the station-proven placement precedent; "the logbook is the system of record … not the bus"; enrichment lives bridge-side by recorded user decision (2026-09-15). external: Wavelog API v2 /lookup returns workedBefore + band/mode flags + confirmed trio + LoTW + flag emoji per call — with no spots endpoint, so per-spot HTTP at cluster rate couples the board's latency to an API; QRZ's free tier (~100 lookups/day, 24 h IP bans) shows the rate wall. Three frames converged here independently.

Rationale

Membership beats lookup on latency, rate limits, cost, and offline operation simultaneously — and the LAN-only principle ("the console must work with no internet beyond the LAN") holds because the set lives on shari. It also gives the draft's status ∈ new|dupe|mult field a real producer at last, and makes the Wavelog mirror load-bearing rather than a passive archive.

Downsides

Sync staleness (minutes) vs per-spot freshness — a spot spotted before its QSO syncs can show ATNO for a short window (mitigated by the flip-on-QSO-event path). Needs the Wavelog mirror to actually run (WaveLogGate UDP from Log4OM). Seed from ADIF/API is the realistic v1; …/log/event exists only in the draft.

3

Spot pipeline: DXLog ingest + event schema + shared rails

Axis: spot pipeline Confidence 75% Complexity M

Description. Get spots onto the bus by extending the bridge that already runs: logger-spot-bridge's deployed UDP listener recognizes — and currently ignores — a spot root in the N1MM/DXLog broadcast family. Wiring that root to the spot stream turns the hardened, seeded, monitored service into the cluster ingest with zero new network surfaces and pre-filtered spots from the logger the operator already trusts; a standalone telnet cluster client (the meta-spotter shape) remains the fallback, not the default. Resolve the written-into-the-docs slot collision (the draft assigns …/spots role bandmap = "DX-spot event source" while the deployed bridge uses the same address for its selection record) via the spid-ercm compound-bridge precedent: one process, two slots, per-slot device_online. Fix the event schema in the same stroke: add the id the draft's own idempotency rule mandates, plus a bridge-assigned stable track identity per (dxcall, band[, mode]) with refresh/drop semantics so re-spot bursts coalesce into one row (spotters[], count) — and land the first shared non-retained event-publish helper in shared/mqtt, which today has none.

Basis

direct: logger-spot-bridge's API doc: "contactinfo/RadioInfo/spot roots are recognized and ignored … the spot stream has no consumer yet"; logger-spot-bridge/CLAUDE.md pins "Log4OM has NO N1MM-style spot/lookup UDP out". Schema gap verified: the draft mandates "Every event carries a stable id" while its §6.3 payload has none. The console ACL conflict is real (broker seed file vs hf_console/CLAUDE.md's "subscribe muehle/#"). external: radar track-while-scan (correlation window, coast, drop) and AIS track fusion for the identity model; Ian Renton's meta-spotter and dh1tw/DX-Cluster-Parser for the telnet fallback.

Rationale

The difference between a new always-on project and a parser extension of a deployed service. Track identity decided in the schema now prevents every consumer from inventing incompatible dedup heuristics (the compass already hand-rolls one, with a documented refresh gotcha); the shared event kit is a conventions act that every future event topic (…/log/event, meters) rides for free.

Downsides

The primary path rests on DXLog actually emitting spot-root datagrams when enabled — not yet live-captured (the telnet fallback hedges this). Slot-topology change touches a deployed service and its docs. The ACL question (does console get event read?) is only moot if idea 1's retained-state shape wins.

Unverified: DXLog spot emission on the LAN needs a live capture before committing (mirror of the Log4OM bare-call capture that gated the selection path). Live-broker ACL enforcement is seed-file-verified, production-untested.
4

Liveness-gated screen-on

Axis: display surface & kiosk Confidence 90% Complexity L

Description. With the surface decided (idea 7 — browser board on :8091, dedicated second tablet), screen-on is a browser concern: acquire the Wake Lock API on first tap after boot/refresh (Chrome on Android supports it; the gesture is required), pair with a CSS night-dim schedule and the true-black scheme, and let burn-in countermeasures ride the table's natural churn plus a slow content shift. The native path stays documented as the alternative: hf_console deliberately removed FLAG_KEEP_SCREEN_ON (commit e05cf64) so the console tablet sleeps after 1 h of touch idle — a policy a permanent board defeats, reversible in native Kotlin beside KioskPolicy if the board ever moves onto that device.

Basis

direct: e05cf64 ("let the display sleep after 1h idle in kiosk — Drop FLAG_KEEP_SCREEN_ON …"); MainActivity.kt: "No FLAG_KEEP_SCREEN_ON: the display should sleep after the system screen-off timeout"; PROVISIONING.md's 1 h touch-idle sleep; the dossier-verified absence of any wakelock/brightness plugin. Five ideation frames converged on this collision. external: digital-signage duty cycles (schedule + content shift, never touch-idle); the Wake Lock API as the browser surface's keep-awake primitive (one user gesture required); STAY_ON_WHILE_PLUGGED_IN as the device-owner lever on the native path.

Rationale

This is the one requirement word — "permanent" — that the current build actively defeats; every other idea is moot if the board is asleep. It reverses a deliberate, recorded decision, so it must be a conscious team act with the burn-in trade-off owned, not a silent revert.

Downsides

Browser keep-awake is weaker than native policy: the lock needs re-acquiring after reboot/navigation and dies when the tab is backgrounded. Always-on-at-brightness is heat and burn-in exposure that needs the dim schedule to be more than a gesture; device-specific Wake Lock behavior on the chosen second tablet is untested.

5

Table grammar: rows, worked ladder, silence

Axis: spot-table UX Confidence 80% Complexity M

Description. The Log4OM-like table doesn't exist (spots are 2.5 px canvas dots today) — so its behavioral contract gets written once, up front, from the repo's own proven patterns.

Rows maintain themselves. One row per track (call|band[, mode]) — the same key at ingest dedup, enrichment updates, and the table widget; re-spots refresh in place with a count column ("×4"); the comment column is an expiry signal ("QRT" kills the row now, "dupe" flags it); age rides the existing fresh/stale/expired buckets with 30 s repaint keys and the 500 ms notify throttle; stable-skeleton in-place row mutation (testui's chooser-snap fix, at table rate). Sort by RF within band groups — Log4OM's own discipline — and never re-sort live: position never fights the eye; new rows settle in.

Worked-before is a 4-rung ladder with a settled color channel. ATNO / new band / new mode / dupe, with a worked-vs-confirmed split. Band colors are fixed hex and "band color wins" is a documented cross-component rule — so worked status needs a deliberate, argued channel (left-edge state stripe, badge column, or row-tint override), not a latent palette clash discovered after theming. Density-adaptive: an empty log makes every row scream ATNO (group ATNOs by DXCC entity into a "needed now" digest); a 50k-QSO log makes every row grey (collapse dupes to counts, float near-misses like "worked 20m cw — now 17m ssb = NEW BAND+MODE").

Designed for its most common state: nearly empty. A blank board reads as broken. A liveness line ("last spot 14 min ago") gated on the two-layer AND (/status + device_online); aged-out rows drift to a dim "recently heard" tail instead of vanishing at the 600 s age-out; and the stream's device_online semantics get defined properly — UDP-silence-is-offline is wrong for a feed where silence is normal. A pit-board glance budget (call in display-scale mono, flag, one worked glyph, band chip, mm:ss, comment — ~5 rows) beats a Log4OM clone squeezed into the 320–420 px side rail at 10–12 px mono.

Basis

direct: selected_spot.dart fresh/stale/expired 5/15-min buckets; compass_panel.dart 30 s repaint keys and the lone age readout "old"; dxspot_service.dart 500 ms throttle, freshest-wins dedup + the receivedAtMs refresh gotcha; testui's stable-skeleton rationale; docs/conventions/band-mode-reference.md: "These are fixed hex values … band color wins when present"; console_screen.dart right-rail geometry (320/420 px); the two-layer liveness convention. external: ED track boards and broadcast tally (escalation color, sort stability); SpotCollector/N1MM bandmaps (re-spots are row updates, never new rows); motorsport pit boards (glance-time budget).

Rationale

Color semantics, merge keys, expiry triggers, and repaint budget form one shared contract every rendering decision depends on — cheap to agree before the table exists, expensive to retrofit. The quiet-band anatomy is the trust contract: distinguishing "band is dead" from "display is dead" is what makes the other 10% of the time believable.

Downsides

Three UX decisions bundled (lifecycle, ladder, silence) — brainstorm should split them if it wants finer grain. The full-screen pit-board framing conflicts with "a panel in the existing rail" until the surface fork (idea 7) is decided.

6

Two-deck propagation: realized above forecast

Axis: propagation panel Confidence 75% Complexity M

Description. A headline strip above the table in two decks, answering the operator's actual question — "which band is open right now" — with two different kinds of truth. Realized deck (client-side): per-band spot rate over a ~15-min window (openness) plus top-quartile SNR trend (quality), derived from the spot data the display already holds — the console already computes this exact metric per grid square, lifted here to band granularity. It can never disagree with the table: it is the table, aggregated. Forecast deck (a new slot): a small shari bridge fetches the hamqsl solar XML (~3 h cadence: SFI, A, K, sunspots, signalnoise, aurora, calculated day/night conditions per band group, VHF conditions) and publishes one retained JSON /state at a doc-first-registered muehle/hf/prop slot. Staleness labeling follows METAR discipline: an index hours old is labeled, not trusted. The forecast deck's per-band verdicts also tint the band-legend chips the panels already draw — one data source, two presentations. WWV/WCY messages already carried on the cluster feed are the zero-marginal-cost alternative source for the forecast deck.

Basis

direct: the propagation axis is a documented zero (repo-wide grep; the reserved "horstprop Layer-3 modelling" hook has never been defined — this is its concrete v0); the meter-stream exclusion precedent ("high-rate, non-retained" — a ~3-hourly retained snapshot is the complementary case the plane discipline allows); the independence rule ("Loss of either feed must never disable the other") maps exactly onto the two-deck split: realized client-side, forecast on the bus. external: hamqsl solar XML field set; QLog renders cluster WWV/WCY as propagation views; METAR+TAF briefing model (obs above forecast).

Rationale

Realized propagation answers "what can I work right now from this receiver" — strictly more actionable than indices and already flowing with zero new external dependency; indices answer "why". The forecast slot gives the bus its first propagation role in a fully conventional retained shape, consumable by every surface at once, and it honors the LAN-only principle (the bridge is the one sanctioned internet place — the CORS precedent from the QRZ web build shows why per-consumer polling fails).

Downsides

FT8/RBN-derived realized conditions measure those modes' activity — label it "measured", not omniscient. The realized deck's source should be the bus bandmap once idea 1 lands (deriving from the horstreporter SSE instead sits awkwardly against the overlay-independence rule). One more tiny service on shari.

7

Surface: browser board on :8091 — decided

Axis: display surface & kiosk Confidence 80% Complexity M

Description. Decided in review (2026-09-19): the "always at the same place" display is a dedicated second tablet running a browser pointed at a board page served by the existing hf-console-web service on shari :8091. Zero provisioning; iteration is ./deploy.sh; browser keep-awake covers screen-on (idea 4); and the operator's console tablet stays untouched as the control tool. The comparison that decided it: a 'dx' page inside hf_console re-earns nothing that isn't already shared through the :8091 WebSocket bridge, but taxes every change with the documented adb-sideload dance (dead LAN mDNS, force-stop no-op on device owner, reboot-to-restart); e-paper wins on physics but constrains color, flags, and refresh, and isn't a tablet. The browser leg's known costs are owned, not ignored: the broader hf-class account in a browser (narrowable later — ACL is per-account, not per-surface) and weaker kiosk guarantees than device-owner lock (mitigate with a full-screen tab plus Android screen pinning, or a thin WebView wrapper, if the board proves out).

First move: prototype the table's legibility before the pipeline lands — a throwaway page reading horstreporter's SSE (or the :8091 WS bridge) with real cluster-family data, so row height, sort stability, and aging behavior are validated at web speed. Known gaps: the console today discards the dxcluster source family at ingest (if (sourceType != 'mqtt') return; — sender/receiver are parsed before the discard), and no comment/mode is parsed; the prototype exists to de-risk UX, not to be the end state.

Escape hatches kept open: if the board later earns a place on the console tablet, the 'dx' page in hf_console (option a) inherits a proven design; if the desire drifts toward an always-on wall board across the room, the e-paper frame (option c) remains the flip, riding idea 1's retained bandmap as a one-topic consumer.

Basis

direct: hf_console/CLAUDE.md web channel — the Go bridge "forwards the /mqtt WebSocket stream byte-for-byte" on :8091; console_screen.dart rail geometry (320/420 px) showing why the console can't host a glance table; PROVISIONING.md's one-way device-owner door. external: DX Cluster Lite's keep-screen-on big-row boards and dxwatch's web walls as the browser-board prior art. reasoned: an unproven UX should iterate at deploy-script speed, and display risk should not share a process with the operator's control console.

Rationale

Surface choice determined the deploy story, the credential exposure, and where the screen-on work is spent — it is now decided, and the data layer (ideas 1–3) is independent of this fork and proceeds regardless.

Downsides

Browser keep-awake is weaker than device-owner policy: Wake Lock needs one tap after reboot and the page can be navigated away. hf-class credentials in a browser on the LAN. Flutter-web rendering performance on a cheap second tablet is untested.
